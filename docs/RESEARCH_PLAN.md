# 연구 목표와 단계별 프로세스

## 최종 목표
제공된 제조 생산·전력 데이터로 전날 16시에 다음 날 96개 15분 구간의 전력을 예측한다. 예측오차와 피크 조건을 분석하고, 조정 가능한 부하가 실제로 존재한다는 가정 아래 30~60분 이동 시나리오를 계산해 한전 요금과 추가 노동비를 함께 고려한 의사결정 기준을 제시한다.

이 연구의 핵심 결과는 ‘정확한 예측 모델 하나’가 아니라 다음의 연결이다.

`데이터 신뢰성 → 시점 누수 없는 예측 → 실패·피크 조건 → 실행 가능한 부하 이동 → 요금·노동비 순이익`

## 단계와 체크포인트

| 체크포인트 | 단계 | 핵심 질문 | 완료 조건 | 현재 상태 |
|---|---|---|---|---|
| CP00 | 문제 정의·환경 | 언제 무엇을 예측하고 누가 어떤 결정을 내리는가? | 예측시점·대상·가정·평가지표 고정 | 완료 |
| CP01 | 데이터 감사 | 시간·결측·중복·단위가 믿을 만한가? | 원본 해시, 시간축 변환, 오류·결측 표 | 완료 |
| CP02 | 예측 실험 | 단순 기준보다 안정적으로 나은가? | 시간 분할, feature ablation, 모델 비교, 고정 선택 | 1차 완료 |
| CP03 | 오류·피크·민감도 | 언제 실패하고 전처리에 얼마나 흔들리는가? | 조건별 오류, 결측·극단값 시험, 중요도, 불확실성 | 1차 완료 |

| CP04B | 운영·경제성 | 예측을 써서 실제로 얼마를 아끼는가? | 에너지 보존 이동기, 동일 조건 비교, 노동비 손익분기점 | 미착수 |
| CP05 | 보고서·발표 | 평가자가 재현하고 의사결정을 이해할 수 있는가? | 실행 notebook, 보고서, 발표, 제출물 검사 | 미착수 |

## 단계별 GitHub 체크포인트 규칙
1. 각 단계 시작 전 `PROJECT_STATUS.md`에서 입력·출력·완료 기준을 확인한다.
2. 코드는 작은 단위로 실행하고 결과는 `outputs/`, 그림은 `figures/`, 판단 근거는 `docs/`에 저장한다.
3. 단계 완료 시 `python run_stage.py check`와 해당 단계 실행을 통과시킨다.
4. `PROJECT_STATUS.md`와 `HANDOFF.md`에 결과, 한계, 다음 명령을 갱신한다.
5. 다음 형식으로 커밋하고 즉시 push한다.

```bash
git add .
git commit -m "CP04A: verify tariff and labor-cost assumptions"
git tag -a cp04a -m "Policy and tariff evidence checkpoint"
git push origin main --follow-tags
```

6. 단계 중간에 30분 이상 재현하기 어려운 계산이 끝났거나 작업을 중단할 때도 `WIP:` 커밋으로 push한다. `HANDOFF.md`에 마지막 성공 명령과 다음 명령을 기록한다.
7. 테스트 결과를 본 뒤 모델·전처리를 바꾸는 후속 실험은 `experiments/<이름>` 브랜치에서 진행하고 기존 CP02 결과를 덮어쓰지 않는다.
8. 공개 저장소이므로 비밀번호·토큰·개인정보를 커밋하지 않는다. 원본 데이터 재배포 조건이 확인되지 않았다는 사실을 README에 계속 표시한다.

## 연구적으로 지켜야 할 경계
- 실제 미래 생산계획인지 불명확한 열을 예측 입력으로 사용하지 않는다. 실제 미래값을 사용한 결과는 oracle로 분리한다.
- 평균오차가 좋아도 피크 탐지가 나빠질 수 있으므로 두 지표를 같이 보고한다.
- 전력량 보존은 생산량 보존을 증명하지 않는다. 설비별 이동 가능 정보가 없어 경제성은 조건부 시뮬레이션이다.
- 역사 최대수요에 묶이면 최대전력 감소가 기본요금 절감으로 이어지지 않을 수 있다.
- 유리한 요금·인건비·기간만 골라 확정 절감액처럼 제시하지 않는다.
