# 연구 중단 후 다른 AI Agent에 이어 맡길 범용 프롬프트

공개 저장소: `https://github.com/pwqppt/kamp-power`

아래 프롬프트는 연구가 어느 단계에서 중단되더라도 사용할 수 있습니다. 특정 단계 번호나 현재 작업을 프롬프트에 직접 적지 않고, 저장소의 상태 문서와 최근 커밋을 기준으로 다음 작업을 판단하게 합니다.

```text
다음 GitHub 저장소의 연구 프로젝트를 기존 설계, 판단 근거, 실험 결과를 보존하면서 이어서 진행해 줘.

저장소: https://github.com/pwqppt/kamp-power

[1. 저장소 준비]
먼저 터미널에서 저장소를 clone해. 이미 clone된 폴더가 있으면 새로 받지 말고 변경사항을 확인한 뒤 최신 main을 pull해.

git clone https://github.com/pwqppt/kamp-power.git
cd kamp-power

작업 전에 다음 명령으로 현재 브랜치, 미커밋 변경, 최근 체크포인트를 확인해.

git status
git branch --show-current
git log --oneline --decorate -10

기존의 미커밋 파일이나 사용자 변경사항을 임의로 삭제하거나 덮어쓰지 마.

[2. 연구 맥락 복원]
코드 수정 전에 아래 파일을 순서대로 끝까지 읽어.

1) AGENTS.md
2) PROJECT_STATUS.md
3) HANDOFF.md
4) docs/RESEARCH_PLAN.md
5) docs/DECISIONS.md
6) docs/DATA_TREATMENT.md
7) docs/NEXT_STAGE.md
8) README.md

그다음 코드, outputs, figures, logs와 최근 커밋을 대조해서 다음 내용을 판단해.

- 연구의 최종 목표와 핵심 메시지
- 완료된 단계와 완료 근거
- 진행 중이던 단계와 마지막 정상 산출물
- 아직 검증되지 않은 가정과 미해결 문제
- 바로 이어서 실행할 가장 작은 단일 작업
- 해당 작업의 완료 조건과 예상 산출물

문서와 실제 파일 상태가 다르면 코드·실행 결과·커밋 기록을 근거로 차이를 밝히고 상태 문서를 바로잡아. 단계 이름이나 번호를 미리 가정하지 말고 저장소의 최신 상태를 기준으로 결정해.

[3. 환경 및 기준점 확인]
README에 따라 가상환경과 의존성을 준비하고 저장소가 제공하는 상태 검사 명령을 실행해. 검사가 실패하면 새 연구를 시작하지 말고 환경 문제인지, 누락 산출물인지, 코드 오류인지 먼저 진단해.

이전 단계가 완료 기준을 충족했고 결과 파일도 유효하면 이유 없이 전체 실험을 반복하지 마. 재현이 꼭 필요할 때만 실행하고, 예상 시간과 덮어쓸 파일을 먼저 확인해.

[4. 연구 연속성 원칙]
기존에 확정한 예측 시점, 데이터 분할, 평가 지표, 모델 선택 규칙, 전처리 원칙과 경제성 가정을 임의로 바꾸지 마. 변경이 필요하면 기존 결과를 보존하고 별도 후속 실험으로 수행해 변경 이유와 비교 결과를 기록해.

테스트 결과를 본 뒤 모델이나 전처리를 소급해 다시 선택하지 마. 미래에 알 수 없는 값을 실제 운용 입력처럼 사용하지 말고, 실제 미래값을 사용한 분석은 참고용 oracle로 표시해. 특징 중요도와 조건별 상관관계를 인과관계로 단정하지 마.

결측치·이상치 처리는 처리 방법, 적용 범위, 학습 데이터에서 계산한 값인지 여부를 기록해. 평균오차뿐 아니라 피크 탐지, 미탐지, 오경보와 민감도 변화도 함께 확인해.

경제성 분석에서는 예측으로 만든 의사결정과 실제값을 본 뒤 만든 의사결정을 구분해. 전력량 보존을 생산량 보존의 증거로 해석하지 말고, 확인되지 않은 단위·설비 제약·요금·인건비는 조건부 가정으로 남겨.

[5. 작업 방식]
한 번에 여러 연구 단계를 벌이지 말고, 현재 진행 중인 단계의 가장 작은 미완료 작업 하나부터 완료해. 작업 시작 전에 다음 세 가지만 짧게 보고하고 바로 실행해.

- 저장소에서 확인한 현재 상태
- 이번에 이어서 수행할 단일 작업
- 완료되면 생성되거나 갱신될 파일

코드, 결과 CSV, 그림, 출처, 가정, 검증 로그를 해당 폴더 구조에 맞춰 저장해. 한글 그림은 프로젝트의 폰트·시간축·단위 표기 규칙을 따르고 축, 범례, 글자 겹침을 확인해.

[6. 체크포인트와 인수인계]
다음 중 하나에 해당하면 즉시 체크포인트를 남겨.

- 한 연구 단계의 완료 조건을 충족했을 때
- 재현 비용이 큰 학습·시뮬레이션·분석이 정상 종료됐을 때
- 중요한 판단이나 가정이 확정됐을 때
- 오류 또는 외부 제약으로 작업을 중단해야 할 때
- 사용 가능한 대화나 실행 시간이 얼마 남지 않았을 때

계정의 정확한 잔여 토큰이나 사용량을 직접 조회할 수 있다고 가정하지 마. 응답 길이 제한, 사용량 경고, 컨텍스트 부족, 도구 호출 실패 반복 또는 작업 중단 가능성이 보이면 새 작업을 시작하지 말고 즉시 현재 결과를 정리해. 장시간 작업은 처음부터 독립적으로 검증 가능한 작은 단위로 나누고, 각 단위가 끝날 때마다 체크포인트를 push해.

체크포인트마다 PROJECT_STATUS.md와 HANDOFF.md를 갱신해. HANDOFF.md에는 마지막 성공 명령, 생성 파일, 검증 결과, 알려진 한계, 다음 한 명령을 적어.

커밋 메시지는 고정된 단계 번호 대신 실제 작업 내용을 설명하도록 작성해.

git add .
git commit -m "checkpoint: <완료한 작업과 핵심 결과>"
git push origin main

중간 상태라면 다음처럼 표시해.

git commit -m "WIP: <현재까지 완료한 내용과 남은 문제>"
git push origin main

태그는 저장소 문서에서 해당 단계의 이름과 태그 규칙이 이미 정의된 경우에만 추가해. GitHub 인증이 없어 push할 수 없으면 로컬 커밋까지 만들고, 실패 원인과 사용자가 실행할 정확한 push 명령을 HANDOFF.md와 최종 응답에 남겨. 업로드하지 못한 상태를 업로드 완료라고 말하지 마.

[7. 공개 저장소 주의]
비밀번호, API 키, 토큰, 개인 연락처와 불필요한 개인정보를 커밋하지 마. 원본 데이터의 권리를 새 라이선스로 주장하지 말고 README의 데이터 공개 주의 문구를 유지해. 원본 데이터와 기존 산출물을 삭제하거나 대체해야 하면 먼저 필요성과 영향을 설명해.

먼저 저장소를 읽고 현재 상태를 복원한 뒤, 판단한 현재 단계와 이번 단일 작업을 짧게 보고하고 실제 작업을 완료 조건까지 진행해. 설명이나 계획만 제시하고 멈추지 마.
```
